# Power BI Reporting — Operational and Actuarial Decision Support

## 1. Objective

The Power BI module provides a unified reporting layer for operational Jira indicators and actuarial SLA risk outputs.

It supports portfolio-level monitoring as well as analysis by client, priority and assignee.

## 2. Data Sources

The reporting model is fed by:

- Prepared SLA ticket data.
- Tables of actuarial results generated by the Python modelling workflow.

The reporting layer therefore combines observed operational indicators with model-derived risk measures.

## 3. Dimensional Model

The project uses an extended dimensional model with four dimension tables and fourteen fact tables.

The model is designed to support multiple analytical views while preserving a consistent reporting structure.

## 4. Report Pages

The report contains five pages:

1. **Risk Exposure** — client and portfolio risk measures, including VaR and TVaR.
2. **SLA Compliance** — SLA performance and breach indicators.
3. **Workload Forecast** — workload-related indicators and projections.
4. **Penalty Analysis** — reporting around the illustrative penalty layer.
5. **Assignee Performance** — workload and SLA indicators by assignee.

The names above are descriptive English labels for the documented page purposes. Keep the labels consistent with the actual published report and screenshots.

## 5. Calculation and Presentation Boundary

The guiding principle is:

**The notebooks calculate; Power BI displays.**

Statistical modelling and simulation are performed upstream in Python. Their outputs are exported into reporting tables. Power BI uses DAX for aggregation, ratios, percentages and context-dependent presentation.

The reporting layer does not independently refit statistical distributions or rerun the actuarial simulation.

## 6. Validation of Reported Values

Displayed indicators were checked against their source values in the model outputs and CSV exports.

The report documents reconciliation checks for key risk and operational indicators. This verifies that the reporting layer reproduces the supplied model outputs without introducing unintended changes.

This is a reporting consistency check; it is not a substitute for statistical validation of the actuarial model itself.

## 7. Integration into SmartDesk

The Power BI report is embedded in the React/Vite application through Microsoft's **Secure Embed** mechanism.

The iframe references a report published in Power BI Service. The viewer authenticates through Microsoft, and access remains subject to Power BI permissions. A Power BI Pro licence is required in the documented setup.

An earlier MSAL-based approach using the “User owns data” model was abandoned because administrator consent on the organization tenant could not be obtained for the project. Secure Embed delegated authentication to the viewer and avoided that application-registration dependency.

Because the embedded report is served from Power BI Service, it is an external service dependency.

## 8. Visual and Semantic Design

The report uses a customized visual theme aligned with the project's corporate context.

Semantic color use and clear labels are important to avoid confusing operational counts, breach indicators and model-derived risk measures.

Assignee performance indicators must be interpreted carefully: a high breach rate does not automatically imply poor individual performance. Priority mix, workload and small sample sizes can affect comparisons.

## 9. Public Presentation

Use only anonymized screenshots. Remove or mask:

- Client names and identifying labels.
- Assignee names and personal information.
- Internal URLs, tenant identifiers and report IDs.
- Any non-public contractual or operational figures.

Do not publish a live Secure Embed URL unless the organization has explicitly authorized public access.
